# coc2 插件接口改造：先改数据形状，再考虑换引擎

> 结论先行：**插件现在的瓶颈不是"用什么引擎跑 JS"，而是"插件能看到什么、能不能回话"。**
> 这两件事都属于接口形状，属于数据形状。先改它们，引擎才有得选；反过来做，等于在一个
> 已经冻结的接口上换发动机，改完还得再改一遍接口。
>
> 三个阶段，每个阶段独立可发布、独立可回滚、独立可验收：
> **① 值 → 引用　② 单向 → 可回值　③ 才谈引擎。**

---

## 0. 先说一个会把人带错方向的实测

我原本以为这条改造的第一优先级是"载荷太大"。实测把这个假设推翻了：

| 场景（coc2 现在的 `Trigger` 原样形状，串行） | p50 | p99 | 吞吐 | 载荷 |
|---|---|---|---|---|
| 空负载 + 插件不读 stdin | **3.08 ms** | 4.05 ms | 320/s | 112 B |
| 空负载 + 插件读完 stdin | 4.86 ms | 6.87 ms | 203/s | 112 B |
| **1 MiB stdout** + 读完 stdin | 5.28 ms | 6.24 ms | 188/s | 1 MiB |
| 1 MiB stdout + 落盘 | 5.41 ms | 6.54 ms | 184/s | 1 MiB |

**1 MiB 载荷只让一次钩子慢了 0.42 ms（+8.6%）；而"起一个什么也不干的进程"本身要 3.08 ms。**

所以在**管道边界**上，字节几乎不要钱 —— 内核拷一遍，插件的地址空间里活得很好，
进程退出就全还给系统，服务器的堆一点没脏。

但这条"字节便宜"的规律**只在进程边界成立**。换成进程内引擎以后，同一份字节要在
**服务器自己的堆里**物化。同一天我在另一个工作负载（8 MiB 请求体）上量到：

| 形状 | p50 | 每次调用堆增长 |
|---|---|---|
| 进程内 JS，载荷 256 B | **1–2 µs** | **0 MB** |
| 进程内 JS，载荷 8 MiB | **10.4 ms** | 每个在飞请求 **30–40 MB** |

**同一个 8 MiB，走管道 +0.4 ms；穿进进程内引擎 +10 ms 和 30 MB 堆。**

这就是整篇文档的支点：**"载荷便宜"这个前提，是进程边界白送的。换引擎就等于把它收回去。**
所以在把边界换掉之前，必须先把接口改成"插件不需要把字节拿到手"。
这就是"先改数据形状，再考虑换引擎"的准确含义 —— 不是因为今天字节贵，而是因为
**换完引擎字节就会变贵，而那时候接口已经不好改了。**

## 1. 现状：现在的插件到底长什么样

### 1.1 形状（全部对应真实代码）

| 事实 | 位置 |
|---|---|
| 发现规则：目录里**一层、只认可执行位** | `internal/server/plugins.go:75-93`（`Mode()&0o111`，`:88`） |
| 调用：`exec.CommandContext` + `hook` 作为 argv[1] | `internal/server/plugins.go:116` |
| 入参：整个载荷 `json.Marshal` 后塞进 stdin | `internal/server/plugins.go:105,117` |
| 出参：`CombinedOutput()` 收下来，**成功时直接丢弃** | `internal/server/plugins.go:152`，消费点只有 `:188`（失败日志里的 `output` 字段） |
| 并发：**每个插件一个 goroutine，没有上限、没有队列** | `internal/server/plugins.go:111-112` |
| 超时：单钩子 5 s，进程组整棵杀掉 + `WaitDelay 2s` 兜底 | `internal/common/limits.go:29`、`plugins.go:124-149` |
| 沙箱：没有。以 server 用户身份执行 | `plugins/README.md` |

四个钩子和它们的载荷 / 频率：

| hook | 触发点 | 载荷 | 最坏大小 | 频率 |
|---|---|---|---|---|
| `agent_connected` | `internal/server/client.go:99` | `agentConnectedEvent`（白名单结构体） | 几百 B | 每次上线 |
| `task_result` | `internal/server/client.go:150` | `protocol.TaskResult` | **≤ 2 MiB**（stdout/stderr 各限 1 MiB） | 每任务结束 |
| `transfer_done` | `internal/server/transfer.go:457` 等 6 处 | `TransferStatus`（路径/大小/校验和） | 几百 B | 每次传输 |
| `metrics_report` | `internal/server/monitor.go:17` | `protocol.MetricsReport` | 几百 B | **每 agent 每 30 s** |

两个数字决定了量级：
- **`TaskResult` 带 `Stdout`/`Stderr` 字符串**（`internal/protocol/types.go:95-102`），
  每个上限 1 MiB（`internal/common/limits.go:19`）—— 这是 coc2 里唯一的"真 blob"。
- **心跳默认 30 s**（`internal/agent/client.go:121-122`）。100 台 agent × 5 个插件 →
  **16.7 次钩子/秒 → 每天约 144 万个进程**。这跟有没有大载荷无关，纯粹是"一个事件一个进程"。

### 1.2 扇出实测（coc2 现在的 `for … go func()` 原样）

| 场景 | 事件 p50 | 事件 p99 | 事件吞吐 |
|---|---|---|---|
| 空负载 × 1 插件 | 4.82 ms | 8.55 ms | 188/s |
| 空负载 × 5 插件 | 8.23 ms | 13.29 ms | 110/s |
| 空负载 × 20 插件 | 25.25 ms | **152.19 ms** | 33.9/s |
| 1 MiB × 5 插件 | 8.74 ms | 9.81 ms | 115/s |

**p99 从 8.55 ms 涨到 152 ms，而每个插件本身只要 3 ms。** 这不是某个插件慢，
是 20 个进程同时抢机器 —— 而这正是"没有准入控制"的直接后果。

### 1.3 四条结构性问题

1. **单向，且输出丢弃**（`plugins.go:161,188`）。插件能说"我看见了"，不能说"我不同意"、
   不能改写、不能拦截。除了写日志和发通知，它做不了任何决策。
2. **载荷只能内联**（`plugins.go:105`）。插件接口和 wire 结构体绑死：`TaskResult` 加了字段，
   插件就自动多收到字段；想让插件自己按需取，做不到。
3. **没有准入控制**（`plugins.go:111-112`）。一个 fleet 抖动（500 台同时重连）就是
   2500 个并发进程。
4. **边界是进程，但不是沙箱**。可执行文件以 server 用户身份跑，能读 `/etc/shadow`。
   "进程隔离"在这里提供的是**健壮性**（崩不到 server），**不是安全性**。

## 2. 为什么必须先改数据形状

### 2.1 理由一：字节便宜是"管道"给的，会随边界一起消失

见 §0 的两张表。同一份 1 MiB：
- 现在：+0.42 ms，代价付在一个随时会死的子进程里，server 的堆完全没碰。
- 换进程内引擎后：要在 server 的堆里物化。按 8 MiB → 30–40 MB 的比例，1 MiB ≈ 4–5 MB；
  5 个插件 × 16.7 事件/秒 ≈ **每秒 400 MB 的分配量压在控制面自己的 GC 上**。

**这句要读两遍：今天大载荷的代价由子进程承担，换引擎后由控制面承担。**
把最容易炸的东西搬进最不能炸的地方，而且是在接口还允许"把整个 blob 内联"的前提下 —— 这是反的。

### 2.2 理由二：现在这个接口，三条路都走不通

想让插件做点有用的事，绕不开这三条，而**每一条都卡在接口形状上，不在引擎上**：

| 想做的事 | 卡在哪 | 是在 `plugins.go` 里改，还是在引擎里改 |
|---|---|---|
| 插件拦下一个任务（策略、白名单） | 输出被丢弃，没有返回通道 | **接口** |
| 插件看一个大对象（传输清单、完整日志） | 只能内联，没有按需取 | **接口** |
| 插件跑十毫秒就要人肉重编译部署 | 必须是可执行文件 | 引擎 |

前两条占了两条，而第三条里"运行形态"恰恰是唯一真正需要引擎的那条。

### 2.3 理由三：改形状可以独立验收、独立回滚；换引擎不行

- 改形状：契约测试 + 冻结的载荷样本（golden payload）就能钉住，跑得比进程快，
  出问题把开关关掉就回到老形状。
- 换引擎：动的是**执行模型**（进程 → 同地址空间）。一旦换了，崩溃隔离、内存隔离、
  权限边界同时失效，回滚等于回滚一次架构变更。它必须**一次就对**。

**先把便宜、可逆的那半做完，是排期问题，不是偏好问题。**

### 2.4 理由四：换完引擎，形状会在最贵的时候被冻结

如果先换引擎，那么"插件拿什么"这件事就被**新引擎的能力**重新定义了一遍：
进程内引擎需要显式装宿主函数、需要 `FromGo` 的转换粒度、需要内存上限。
到那时再改形状，等于在**一个已经上线、已经有人在写插件**的接口上做破坏性变更，
并且这次破坏性变更多的成本落在"内部对象怎么跨边界"这种最难解释的地方。

**接口定在前面，引擎跟着接口挑** —— 引擎是接口的实现细节，不是反过来。

## 3. 阶段一：把"值"改成"引用"

**目标：插件不再"收到载荷"，而是"收到载荷的地址"。** 不改引擎，不改传输，不改语义。

### 3.1 新契约

事件信封从"结构体本身"变成：

```json
{
  "schema": 2,
  "event": "task_result",
  "id": "evt_01J...",          // 事件自己的 id，可用于回查和幂等
  "at": "2026-10-22T07:30:00Z",
  "ref": "/api/v1/events/evt_01J...",   // ★ 取完整载荷的地址（operator 面，走现有 bearer token）
  "hint": {                          // 让插件不取也能干活的最小摘要
    "task_id": "t-0001",
    "agent_id": "ag-0001",
    "status": "failed",
    "exit_code": 1,
    "stdout_bytes": 1048576,
    "stderr_bytes": 0
  }
}
```

要点：
- **`hint` 是形状的边界，不是顺手给的**。它必须够一个"只想知道发生了什么"的插件用；
  想知道细节的，按 `ref` 自己取。
- `ref` 只能由 server 自己签发的 `evt_` id 解析，**不能是文件路径、不能是任意 URL**
  （否则一个恶意插件就能让 server 去读任意文件 —— 现在它已经有这个能力了，别再扩大）。
- 插件没装 HTTP 客户端也能工作（读 `hint`），所以这是**纯增量**。

### 3.2 分层规则（哪条进 `hint`，哪条进 `ref`）

判据一条：**"不取 `ref` 也应该能做完最常见的那个判断"**。

| hook | `hint` 里必须有 | 只能从 `ref` 拿 |
|---|---|---|
| `agent_connected` | 全部字段（本来就小） | — |
| `task_result` | `task_id` / `agent_id` / `status` / `exit_code` / `duration_ms` / 两个 `*_bytes` | `stdout` / `stderr` 正文 |
| `transfer_done` | `transfer_id` / `agent_id` / `status` / `size` / `checksum_sha256` | 路径细节、分块信息 |
| `metrics_report` | 全部字段（本来就小） | — |

★ 一条硬规则：**`hint` 里永远不放正文**。`task_result` 现在把 1 MiB stdout 内联，
是唯一会打破"字节便宜"假设的地方，把它挪到 `ref` 后面，§2.1 那条 GC 风险就消失了。

### 3.3 落地改动（都在 `internal/server`，不碰 wire 协议）

| 改动 | 位置 | 说明 |
|---|---|---|
| 新增 `internal/server/plugin_event.go` | 新文件 | 信封类型 + `hint` 构造 + `schema` 版本 |
| `Trigger` 签名加 `eventID` | `plugins.go:100` | 由调用点生成，`common/id.go` 已有 id 工具 |
| 新增事件读取端点 | `internal/server/hub.go:367` 的 `operatorRoutes` | `GET /api/v1/events/:id`，挂在现有 `requireOperatorAuth` + `oplogMiddleware` 后面（跟 `:440` 的 `GET /api/v1/plugins` 同一层）。**只认本进程签发的 id**，5 分钟过期 |
| 四类载荷的 `hint` 投影 | 四个调用点 | `task_result` 的正文**只进存储，不进信封** |
| 插件侧存根 | `plugins/` | 一个 `curl` 一行就能取，README 里给可跑的例子 |

★★ **`ref` 的凭据是阶段一唯一的新增安全面，而且不能走捷径。**
现在的 operator 面只有一个 token（`hub.go:1074` 的 `s.cfg.APIToken`），**没有 scope、没有只读变体** ——
所以"把 operator token 给插件"等于把整个控制面交出去（能给任意 agent 派任务、能删数据）。
`plugins.go:34-40` 已经为"别把 fleet token 递给插件"立过规矩，这里别破第二次。

→ 阶段一必须**新发一种只读事件凭据**（只允许 `GET /api/v1/events/:id`，绑定到具体 hook），
随插件目录一起下发，可单独吊销。这条是阶段一的**前置条件**，不是可选项：
没有它，`ref` 就只能靠"知道 id 就能读"，那比现在更糟。

### 3.4 兼容

- 用 `-plugins-envelope=v1|v2` 开关，默认 `v1`。
- `v2` 下同时提供 `COC2_PLUGIN_ENVELOPE=v2` 给插件判断。
- **不提供"v2 但正文也内联"的中间态** —— 那会把两个问题绑在一起，永远分不清是谁的锅。

### 3.5 验收（含反证）

1. 四个 hook 各跑一遍，断言信封里 `hint` 的字段集**恰好等于**上面那张表（多一个字段就失败）。
2. **反证 `task_result` 不内联**：造一个 1 MiB stdout 的任务，断言信封体积 < 4 KiB。
   （这条是本阶段唯一实质性的性能承诺，必须被钉住。）
3. `ref` 取回的字节与 store 里的逐字节相同（含 truncation 标记）。
4. **伪造 `ref` 必须失败**：`ref` 指向 `file:///etc/passwd`、指向别人的 event id、
   指向过期 id —— 三种都断言拒绝，且**一个文件都没被读**（用 `strace`/探针文件证）。
5. 老插件（只读 stdin、不取 ref）在 v2 下仍然正常工作 —— 这是整个阶段的安全网。

## 4. 阶段二：从"单向通知"到"可回值"

这才让插件变成插件，而不是日志消费者。**依然不换引擎。**

### 4.1 信封的第二个方向

```json
// 插件写到 stdout 的最后一行（或 fd 3，见 §4.4）
{"schema": 2, "decision": "deny", "reason": "…", "correlation": "evt_01J..."}
```

三个判定：

| `decision` | 含义 | server 行为 |
|---|---|---|
| `allow` / 无输出 | 默认，等于现在 | 照常执行 |
| `deny` | 拦下这个动作 | 按 §4.2 的钩子表处理 |
| `defer` | 需要更多信息 | 记 audit，按默认放行（**不阻塞**） |

### 4.2 哪些钩子允许 `deny`，哪些只是通知

**这是本阶段最容易做错的地方。** 一个钩子能不能拦，取决于它所在路径能不能等：

| hook | 能 `deny` 吗 | 理由 |
|---|---|---|
| `task_result` | ✗ 只是通知 | 结果已经发生，拦它只会丢数据 |
| `transfer_done` | ✗ 只是通知 | 同上 |
| `metrics_report` | ✗ 只是通知 | 30 s 一次的热路径，见 §4.3 |
| `agent_connected` | **✓（需要一个新的 `task_dispatch` 钩子配套）** | 想拦任务，得拦在**派发前**，不是上线时 |

★ 换言之：**要做策略，缺的不是"返回值"，是"派发前的那个钩子"。**
`task_dispatch` 是阶段二真正要新增的东西，`agent_connected` 不是它的替身。
这条如果搞混，就会做出一个"能拒绝但拒绝得没意义"的接口。

### 4.3 热路径不能等

`metrics_report` 是 16.7 次/秒 × 超时上限 5 s —— 只要等一次就等于把心跳拖死。
所以：
- **只有 `task_dispatch` 是同步的**（它有明确的、可等的预算，比如 200 ms）。
- 其余四个保持 fire-and-forget，**永远不等输出**。
- 同步钩子的预算必须**小于**调用方的超时（任务派发本身有自己的预算），
  并且**超时 = 放行**（fail open），同时记一条 audit —— 降级必须是显式的、可见的。

### 4.4 输出通道的形状（这里有个坑）

现在 `CombinedOutput()`（`plugins.go:152`）把 stdout 和 stderr 合并了。
一旦 stdout 要承载结构化返回，**stderr 里的任何一行日志都会污染解析**：

| 通道 | 用途 | 现状 |
|---|---|---|
| stdout | 结构化返回（一行 JSON） | 和 stderr 合并 ❌ |
| stderr | 给人看的日志 | 同上 |

**改法**：stdout / stderr 分开捕获（`cmd.Stdout` / `cmd.Stderr` 各一个 `cappedBuffer`，
`internal/agent/client.go:473` 已有现成的类型可抄），
只解析 stdout **最后一行**，其余当日志。
★ 这一步必须在开放"返回值"之前做 —— 否则每个插件作者都会**静默**踩到它，
症状是"我的 deny 不生效"，而且只在插件打了日志的时候复现。

### 4.5 会破坏的既有语义（要显式改，不要偷偷改）

`TestPluginTriggerReturnsBeforePluginFinishes`（`plugins_contract_test.go:229`）
是在**钉住**"Trigger 立刻返回、不等插件"这条语义的。阶段二引入同步钩子时：
- 对 `task_dispatch`：**这条测试应该失败**，然后改成一个新的契约测试
  （`TestTaskDispatchWaitsForDecision`），并保留旧的用于另外四个钩子。
- **不要为了让老测试过而把同步钩子做成异步** —— 那就等于没做。

### 4.6 验收

1. `task_dispatch` 返回 `deny` → 任务不派发，audit 有一行，agent 侧收不到任务。
2. 插件超时 200 ms → 任务**照常派发**（fail open），audit 里有 `decision=timeout`。
3. 插件在 stderr 打 10 行日志 + stdout 一行 `deny` → 仍然正确解析出 `deny`（§4.4 的回归）。
4. 恶意返回：非 JSON、超长行（>64 KiB）、`decision` 是未知值 → 一律当 `allow` + audit。
5. `metrics_report` 钩子挂住 5 s → **不影响心跳**（这条用注入式反证：让钩子 `sleep 10`，
   断言心跳仍在 30 s 内完成）。

## 5. 阶段三：现在才谈引擎

### 5.1 候选与判据

**判据不是"哪个快"。** 到这一步，延迟已经由"要不要跨进程"决定，而引擎之间的差距
在这个量级上不重要（前面测过：空载荷 1–2 µs vs 进程 3 ms）。真正的判据是三条边界：

| 候选 | 崩溃隔离 | 权限边界 | 内存可控 | 插件成本 | 换它的真实代价 |
|---|---|---|---|---|---|
| **现状：独立进程** | ✓ 完整的 | ✗ 无沙箱（以 server 用户跑） | ✓ 进程级 | 编译+分发 | — |
| **进程内纯 Go JS（moejs 等）** | ✗ 崩到 server | △ 靠引擎的全局/宿主函数白名单 | ✓ 引擎限额（含脚本 catch 不住的那种） | 写 JS，热更新 | 失去崩溃隔离；`MemoryLimit` + 任意 goroutine 中断是唯一护栏 |
| **独立 sidecar（一个常驻 JS 进程）** | ✓ | ✓ 可以降权、可以 `ProtectSystem` | ✓ | 写 JS，热更新 | 多一个要管的服务；跨机要认证 |
| **代码生成到 Go** | ✓ | ✓ | ✓ | 改完要重编译 | 等于没有插件 |

**我的判断：如果目标只是"让插件好写"，sidecar 大概率比进程内 JS 更对。**
理由是这里的边界本来就是"控制面 vs 插件"，进程内只是在省那 3 ms —— 而 3 ms
对 `task_dispatch` 的 200 ms 预算完全不构成压力。**用一个可杀的进程保住崩溃隔离，
比省 3 ms 值钱得多。**

**moejs 这类进程内引擎真正值得用的前提是：插件数量大到"每事件一进程"变成结构性成本**
（比如 1000 台 × 10 个插件 = 167 进程/秒、每天 1400 万个进程）。
到这个量级之前，换引擎的收益是 3 ms，代价是崩溃隔离 —— 不划算。

### 5.2 进入阶段三的门（gate）

**四条全中才动手，缺一条就继续待在 sidecar：**

1. 进程创建成为可测量的瓶颈：`sys` CPU 占 server 总 CPU 的 **> 25%**，或钩子 p99 **> 50 ms**。
2. 插件侧已经稳定（阶段一二上线 ≥ 1 个月，无破坏性契约变更）。
3. §3 的 `ref` 已经生效 —— **`task_result` 的信封里不含正文**。
   （没有这条，换引擎就是把 §2.1 那个 GC 风险直接搬进控制面。）
4. 崩溃隔离有替代品：至少做到"每个插件一个 runtime + 内存上限 + 能中断死循环 + panic 不带走 server"，
   并且**注入式验证过**（不是文档说支持就信）。

### 5.3 换引擎时唯一不能省的三条

如果真走到这一步：

1. **每个插件独立 runtime**，不给"共享一个 runtime"留口子（否则一个插件污染全局，全 fleet 遭殃）。
2. **内存上限开着**，且验证过"脚本自己 `try/catch` 也拦不住"。
3. **插件拿不到 `ref` 以外的任何宿主能力** —— 宿主函数白名单，`eval`/`new Function` 关掉。

## 6. 顺序反了会怎样（推演，不是假设）

**如果先换引擎（进程内 JS），不做形状改造：**

1. `task_result` 仍然内联 1 MiB stdout → 每个插件一次 1 MiB 进 server 堆。
5 个插件 × 16.7 次/秒 ≈ **每秒 400 MB 分配**落在控制面。
2. 为了压住 GC，提高 `GOGC` 或设 `GOMEMLIMIT` → 分两档都实测过：
   `GOGC=300` 堆涨 2.3 倍吞吐反降；`GOMEMLIMIT` 贴着上限反复 GC，
   p99 从 392 ms 变 **1.06 s**。**这不是配置问题，是分配量问题。**
3. 于是不得不回去改形状 —— 但这时插件已经有人在写，改动是破坏性的，
   而且**新的执行模型又反过来限制形状**（进程内引擎对"跨边界对象"有它的脾气）。
4. 最后拿到的是一个**既失去了崩溃隔离、又没治好载荷**的版本。

**反之（先形状、后引擎）：**
1. 阶段一二独立上线，每一阶段都能用现有测试体系验收，随时可关。
2. 阶段三的门如果一直不满足，就一直停在"独立进程/sidecar"——
   **这不是失败，是正确的停止点**：3 ms 的进程开销换完整崩溃隔离，是划算的。
3. 真到了要换的那天，接口已经是引用式的，换完不需要再改形状。

## 7. 一页看完

| 阶段 | 改什么 | 碰不碰引擎 | 可独立发布 | 关键验收 |
|---|---|---|---|---|
| 一 | 值 → 引用（信封 + `hint` + `ref`） | ✗ | ✓ | 1 MiB stdout 的信封 < 4 KiB；伪造 `ref` 被拒 |
| 二 | 单向 → 可回值（`task_dispatch` 同步，其余不等） | ✗ | ✓ | deny 生效；超时 fail open；stderr 不污染解析 |
| 三 | 引擎（大概率是 sidecar，不是进程内） | ✓ | ✓ | 四条 gate 全中才动 |

三个阶段之间**没有依赖倒置**：一 → 二的依赖是"信封"，二 → 三的依赖是"信封里没有正文"。
任何阶段停下来，系统都是完整可用的。

## 8. 明确不做（减法）

- **不做插件市场 / 不做版本协商协议**。`schema` 字段够用，别提前发明生态。
- **不给插件任意文件系统访问**。现在它已经有这个能力了（以 server 用户跑），
  但**不要在接口上把它变成承诺**。
- **不为了"统一"把所有钩子做成同步**。热路径必须永远异步，见 §4.3。
- **不追求"零拷贝"**。这个量级（3 ms 进程、1 MiB 载荷）里，零拷贝是过早优化。
- **不在阶段一二里顺手换引擎**。哪怕它看起来只改一个 import。

## 9. 实施记录（2026-10-22）：三个阶段一起落地，引擎选了进程内 moejs

**这一节是事后写的，不改上面任何结论 —— 它记录的是业主的决定，以及那个决定要成立必须补上的东西。**

业主的要求是「按最新修改的文档对插件模块进行改造，采用 moejs」。
所以**阶段一和阶段二先做**（§3、§4 的接口），**阶段三同批做完**（引擎换成
[moejs](https://github.com/Calcium-Ion/moejs)，纯 Go、Apache-2.0）。顺序仍然按本文的：
形状先定，引擎后接。§6 那条"先换引擎会怎样"的推演因此没有被踩。

### 9.1 为什么这里敢越过 §5.2 的四条 gate
§5.2 的四条是"继续待 in-sidecar"的判据，其中第 3 条（`ref` 已生效、信封不含正文）
和第 4 条（每插件独立 runtime + 内存上限 + 能中断死循环 + panic 不带走 server，
且**注入式验证过**）是**可以当场满足的**，这批改造把它们满足了：

| §5.2 的 gate | 现在的状态 |
|---|---|
| 3. `ref` 生效、`task_result` 信封不含正文 | ✅ `TestTaskResultEnvelopeCarriesNoBody`（1 MiB 结果的信封 < 4 KiB） |
| 4. 每插件独立 runtime / 内存上限 / 可中断 / panic 不带走 server | ✅ 见 9.2 的表，逐条有测试，且**注入缺陷验证过有牙** |

第 1 条（进程创建成为可测瓶颈，`sys` CPU > 25% 或 p99 > 50 ms）**没有达成，也没打算假装达成**。
也就是说：这次换引擎**不是被性能逼的，是产品决定** —— 让插件能"改完即生效、不用编译分发"，
并且能回值（§2.2 的第三条路）。**代价明码标价写在 §5.1 和 9.3：丢掉崩溃隔离。**

### 9.2 换引擎时"唯一不能省的三条"（§5.3）落到哪
| §5.3 要求 | 实现 | 验证 |
|---|---|---|
| 每个插件独立 runtime，不给共享留口子 | `jsPlugin` 自己持有 `idle` 池；管理器从不跨插件借 runtime | `TestPluginIsolation`（A 写的 global，B 读到 `undefined`） |
| 内存上限开着，且脚本 `try/catch` 拦不住 | `Options.MemoryLimit` = 32 MiB，引擎以**中断**执行 | `TestPluginMemoryLimitCannotBeCaught`（注入"关掉上限"→ 测试挂） |
| 插件拿不到 `ref` 以外的宿主能力；`eval`/`new Function` 关掉 | 只装 `console` + `coc2` 两个全局；`DisableDynamicCode: true`；没装 `Importer` | `TestPluginDynamicCodeIsDisabled`、`TestPluginEventFunctionRejectsForeignIDs` |

另外补了 §5.1 没提但同样致命的一条：**死循环必须能被外部停掉**，
否则"一个插件写错 while"就是整个控制面。`TestPluginHookTimesOut` 用 100 ms 预算跑 `for(;;){}`，
测到的是**中断生效**，不是"插件很乖"。

### 9.3 明确被放弃的那条
**崩溃隔离。** 引擎是普通 Go 代码，它自己的 bug 能打到 server；一个插件不再有自己的地址空间。
缓解：panic 变成 error（引擎行为，有测试覆盖），调用一律有预算并被中断，
每个插件有内存上限；剩下的是引擎缺陷，不是插件代码。
§5.1 那句判断（"如果目标只是让插件好写，sidecar 大概率更对"）**依然成立**，
这次是拿它换"不用编译分发"这个产品收益。**要回到 sidecar，接口不用再改** —— 这是 §3 先把形状做完的好处。

### 9.4 顺带做掉的两件小事
- **准入控制**（§1.3 第 3 条）：`PluginMaxConcurrentHooks = 64`。异步钩子超出**丢弃并 warn**
  （通知型事件丢了比积压好）；同步的 `task_dispatch` **不丢**，它在自己的 200 ms 预算里等。
- **可执行插件**保留但标弃用，并且能吃新信封（`-plugins-envelope=2` + `COC2_PLUGIN_ENVELOPE=2`），
  这样升级不会打断已在跑的老插件 —— 这是 §3.4 的兼容要求。

### 9.5 真机跑起来才发现的三处（单测当时是绿的）
1. **超时的钩子完全没有日志**。JS 插件没有退出码、没有 stderr，`Trigger` 又是 fire-and-forget
   把 error 丢了 → 「每次都超时」和「根本没被调用」在日志上完全一样（正是 §1.1 那条可观测性
   问题的镜像）。活体复现：一个 `for(;;){}` 的 `metrics_report` 插件，心跳照常、日志一个字没有。
   现在 `Run` 自己记 `plugin hook timed out` / `plugin hook failed`（带 `js_stack`）/
   `plugin hook exceeded its memory limit`，并有 `TestTimedOutAsyncHookIsLogged` 钉住。
2. **可执行插件被拉进了同步决策**。它没有返回通道，去问它等于在派发路径上白 fork 一个进程，
   还会留下一条误导性的 `decision=timeout` 审计。现在 `pluginRunner.Decidable()` 把它们排除。
3. **读 `stack` 是个执行插件代码的动作**。抛出的对象可以自带一个死循环的 `stack` getter，
   而"读栈"发生在失败路径上。现在它有自己的 50 ms 预算 + 中断 + `recover`，
   并有 `TestHostileStackGetterCannotStallTheServer`（这条测试第一次写弱了：
   钩子自身的 5 s 预算会兜住读操作，所以 50 ms 和 100 s 的注入都"通过" —— 改成
   「必须在钩子预算的 1/5 内报出来」之后注入才挂）。

### 9.6 新增的东西（都写进 `coc2 schema` 的 limits 了）
`plugin_decision_timeout_secs` · `plugin_max_concurrent_hooks` · `plugin_max_runtimes_per_plugin` ·
`plugin_memory_limit_bytes` · `plugin_event_ttl_secs` · `plugin_envelope_schema` ·
新端点 `GET /api/v1/events/:id`（信封里 `ref` 指向它）· 新 hook `task_dispatch`。

## 附录 A：本文的数字是怎么来的（可复现）

- 进程成本 / 扇出：按 `internal/server/plugins.go` 的**原样形状**复刻
  （`exec.CommandContext` + `Setpgid` + 自定义 `Cancel` + `WaitDelay` + `CombinedOutput`），
  插件是 `#!/bin/sh` 脚本，串行 300 次取 p50/p99，扇出用"一个事件开 N 个 goroutine"。
  **本机 macOS / 10 核**，所以绝对值偏乐观 —— VPS 上只会更慢，不会更快。
- 进程内引擎的对照：同一个工作负载（8 MiB 请求体、64 并发）在 `moejs` 上测，
  冷启动 1.4–2.4 µs、空转 runtime 5.9 KiB、8 MiB 载荷 p50 10.4 ms。
  **注意不是同一个任务**：它是"HTTP 请求体 + 一次 JS 调用"，这里是"一次钩子"。
  用它只为说明一件事：**同样的字节穿进进程内引擎会物化，走管道不会。**
- `GOGC` / `GOMEMLIMIT` 那三档也是在 8 MiB 负载下量的，别当成 coc2 现在的数字。

**一句话：本文里 coc2 的数是自己量的，引擎的数是借来的对照，别混着引。**
